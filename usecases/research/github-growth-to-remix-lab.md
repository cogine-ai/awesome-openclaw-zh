# 新玩法雷达：从 GitHub 信号到周末复刻实验

> 每次找一个正在获得关注的项目，做出能分享的最小复刻，而不只堆一份热门链接。

## 来源与验证说明

- 类型：Cogine 原创实验；2026-10-11。
- 依据：OpenClaw 的网页检索、浏览器与 workspace 文件工具，配合 GitHub 官方 API。
- 与科技日报、市场研究的区别：要求保存证据、挑一个可复刻玩法、留下实际产物，再形成下一次选题输入。
- 状态：工作流设计与最小数据样本；尚未实测完整网络检索及复刻链路。

## 前置条件与成本

能访问公开网页的 Agent。GitHub 公共 API 有限流；认证令牌应由运行环境提供，避免写入提示词和报告。首次体验可使用下面的离线数据，不需要令牌。

## 快速体验版（先跑一轮）

```text
请按“有证据的关注变化→一个有趣玩法→一份最小实验计划”整理下面虚构数据。
这些不是任何真实项目的统计，不要写成新闻。

A：两次同口径快照相隔7天；Star从180到260；演示为PDF转漫画；最近发布3天前；需要图像API。
B：只有今天30000 Star；演示为实时视频助手；没有历史快照；需要眼镜和私人测试账号。
C：两次同口径快照相隔7天；Star从20到50；演示为单文件交互故事；最近发布2天前；普通浏览器即可。

输出 research.md：
1. 表格列出累计关注、净增加、相对变化、样本局限。
2. B的增长写“未知”，不得用累计30000推断正在暴涨。
3. 兼顾绝对新增、门槛和可展示性，推荐一个一天内能完成的实验；允许推荐C，但解释小基数。
4. 写最小输入、产物、验收动作、费用未知项与下一次需要补的证据。
5. 最后拟一条只描述真实产物的分享文案，署名“OPCBoost · by Cogine”。
```

答案核对：A 净增加 80，相对增加约 44.4%；C 净增加 30，相对增加 150%；B 无法计算增长。高百分比不等于更大的新增规模。

## 换成真实项目

1. 选 5 个候选，保存 API 返回的 `stargazers_count`、`created_at`、`pushed_at` 与采集时间。区分推送、Release 和作者演示日期。
2. 如有同口径历史快照，计算净变化；没有快照就记录“当前关注度”与“创建以来积累”，不补造一周涨幅。
3. 读作者 README、安装说明与演示，核实它支持 OpenClaw 的具体方式。
4. 只挑一个低门槛、有可展示产物的题目，先做本地最小复刻。
5. 保存版本、输入、步骤、产物与失败原因；真实完成后再形成发布素材。

可要求 Agent 使用网页工具读取 `https://api.github.com/repos/OWNER/REPO`。限流或访问失败时记录失败并转作者 Release/演示证据，不要重复重试来制造“数据”。

## 成功标准

- [ ] 每个真实数值有来源和采集时间，虚构样本有明确标记。
- [ ] “已复刻”有实际产物；只完成研究的标记为选题。
- [ ] 每轮保留一个失败记录和一个新的组合想法。

## 延伸玩法

把同一机制用于新插件、新视频模型或新移动端能力。研究雷达需要人工启动；用户决定节奏后再配置调度。
